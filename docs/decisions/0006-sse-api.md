# ADR 0006：SSE 串流 API

狀態：已採用（Step 6）。

## 背景

`POST /api/ask` 要邊算邊把進度與答案送給前端：每個步驟的狀態、檢索結果、逐段答案與引用、驗證結果。要處理：串流中途出錯、使用者斷線、付費 API 被濫用、模型輸出的標記被切在兩段之間。

## 決定

| 項目 | 決定 | 放棄了什麼 |
|---|---|---|
| 傳輸 | SSE（`text/event-stream`），POST 帶問題，前端用 `fetch` 加 `ReadableStream` 解析 | WebSocket：雙向用不到、要自己處理重連與代理；瀏覽器原生 `EventSource`：不能 POST |
| 事件格式 | 每個事件 `event: {type}` 加 `data: {外框 JSON}`；外框 `{type, run_id, ts(毫秒), data}`；Pydantic 判別聯集定義，測試驗證每個事件符合 schema | 手寫 dict：欄位拼錯只有前端才發現 |
| 同步／非同步 | 事件產生器是**同步**的，在 HTTP 層用執行緒池逐個取事件 | 全面改成 async：SDK 與 Chroma 的同步呼叫會阻塞事件迴圈，要整套改寫 |
| 斷線 | 每送一個事件檢查一次斷線，另外 Starlette 偵測斷線時取消；`finally` 關閉事件產生器，連帶關閉對模型的串流（`GeneratorExit` → 離開 `with stream`） | 不處理：使用者關掉頁面後仍繼續付費產生答案 |
| 心跳 | 15 秒沒有事件就送 `: keep-alive` 註解行 | 不送：模型思考較久時中間的代理可能關掉閒置連線 |
| 錯誤 | 串流開始後的任何失敗都轉成 `error` 事件，然後正常結束串流；訊息為固定的中文說明，不含內部細節（細節只記在 log） | 拋出例外：狀態碼已是 200，前端只會看到「連線中斷」 |
| 串流中的標記 | 小型狀態機：標記沒收完整前先暫存，保證送出的 delta 不含半個標記；開頭先暫存約 10 個字元確認不是 `[[REFUSE]]` | 把標記切點交給前端處理 |
| 速率限制 | 每個來源 IP 每 60 秒最多 10 次（可設定），超過回 429 加 `Retry-After`；無效請求（422）不計入 | 全域限制：一個人用完大家都不能用 |
| 問題長度 | 上限 200 字（超過回 422）、去除前後空白、空白問題回 422 | |
| 逾時 | 對 Claude 的連線與兩段資料之間最久等 60 秒 | SDK 預設 10 分鐘 |
| 依賴建立 | 第一次用到時才建立索引與模型客戶端；失敗回 503；線上不寫磁碟的問題快取 | 啟動時建立：沒有金鑰或索引時連 `/api/health` 都無法啟動；磁碟快取：多個請求同時寫同一個檔、也不該把使用者問題落地 |

## 與 spec 5.3 的對照與細節（前端須知）

- **`answer.delta` 的文字保留原樣的 `[[…]]` 標記**，緊接著送 `answer.citation {marker, chunk_id}`。前端在串流中把標記顯示成不可點的樣式，完成後替換成 CitationBadge。標記一定是完整的（不會被切在兩個 delta 之間）。
- **`answer.citation.chunk_id` 是「條」（`K0040012:35`），`retrieval.results` 的 `chunk_id` 是檢索到的那一塊（可能是 `K0040012:35-p2`）。** 兩者去掉 `-p{n}` 後即對應同一條。因為模型看到的是整條條文，引用的單位就是條。
- **`rewrite` 步驟一律送出**（未啟用時摘要為「未啟用」，`rewrite.result` 的查詢只有原始問題），讓畫面的五個步驟固定。`rerank` 沒有做，不送事件。
- **`retrieval.results` 送前 5 條**（與模型看到的一致），每筆含 `law_name`、`law_short_name`、`source_url`、`amended_date`，卡片不需要再逐筆打 API。`score` 是餘弦相似度。
- **兩種拒答**：門檻擋下送 `answer.refused {reason: "low_relevance"}`，後面的步驟不送；模型拒答時 `generate` 步驟會先送 `step.completed`（摘要「條文不足，模型拒答」）再送 `answer.refused {reason: "out_of_scope"}`；兩種都帶 `top_score` 與 `threshold`，然後 `run.completed`。
- **`error` 之後不會有 `run.completed`**，串流直接結束。錯誤之前已送出的 delta 仍然有效，前端應保留並提示「答案不完整」。
- **429 帶 `Retry-After`（秒）**，CORS 已設定讓前端的 `fetch` 讀得到這個標頭。
- 驗證步驟只送引用的驗證結果（spec 的 `validate.result` 只有 `valid`／`invalid`）；答案中的**數字檢查**沒有放進事件，結果只記在 server log，供追查。
- `GET /api/chunks/{chunk_id}`：除了切塊 id，也接受「條 id」（引用事件用的），此時以該條的第一塊的欄位加上整條 `article_text` 回應。

## 實測

用真實索引與 `claude-sonnet-5-5`（改寫關）以 `curl -N` 驗證：一般回答第一個字約 1 秒後送出，引用標記完整成一個 delta、緊接著 `answer.citation`；總耗時約 2.4 秒（檢索約 0.4 秒、生成約 2 秒）。門檻擋下（「今天天氣怎麼樣？」最高 0.26）全程 264 ms，沒有呼叫模型；模型拒答（「公車專用道可以走嗎？」）約 1.7 秒。201 字與空白問題回 422；第 5 次請求回 429 加 `Retry-After`；使用者 2 秒後斷線，伺服器立刻記錄「提早結束」，沒有錯誤堆疊。

## 限制

- **每個進行中的串流會佔用一個執行緒**（同步產生器），執行緒池預設約 40 個，同時進行的串流超過這個數字就要排隊。在每 IP 每分鐘 10 次的限制下，作品集 demo 夠用；要承載更多流量，需改成 async 的 SDK 與非阻塞的檢索。
- **速率限制存在程式記憶體**：只對單一實例有效、重新啟動後歸零；多實例部署要改外部儲存。`X-Forwarded-For` 只有設定 `TRUST_PROXY=true` 才採信，並取最後一個值（我們的代理加上去的）；前面的值是用戶端自己填的，可偽造。
- **斷線偵測的延遲**：正在等模型回下一段時無法中斷那個阻塞呼叫，所以斷線後可能還會多收一兩段才真正關閉模型串流（實測約在斷線的同一秒內關閉）。
- **模型中途才輸出 `[[REFUSE]]` 的極端情況**：已送出的文字無法收回，會先看到文字，再收到 `answer.refused`。prompt 要求拒答時只輸出標記，評估中沒有出現過。
- **安全機制 fallback 在串流模式未被實際觸發過**，行為未驗證（API 接受參數）。
- 沒有身分驗證；速率限制只能擋誤用，擋不住有意的分散式濫用。
- 未涵蓋瀏覽器端：前端的 `fetch` 串流解析（Step 7）、經 nginx 等代理的緩衝行為（Step 12 部署時要實測）。

## 後果

- 事件的 schema（`app/schemas/events.py`）是前後端的契約；Step 7 的 `types/events.ts` 要依它手寫（或另外產生）並保持一致。
- 串流版與非串流版（`answer_question`，評估用）有重複的流程；有測試驗證兩者對同樣的模型輸出結論一致，改其中一個要記得另一個。

## 獨立 review 後的修訂

- **答案被長度上限截斷**（`stop_reason == "max_tokens"`）改送 `error` 事件，代碼 `truncated`，不再當成完整答案走到驗證與 `run.completed`。
- 偵測到回答開頭的 `[[REFUSE]]` 後立刻停止讀取模型串流（原本會讀到結束，持續計費）。
- 串流解析器：單獨的 `[[` 之後又出現 `[[` 時，前者視為文字，後者重新判斷，不再連帶吞掉後面的真引用。
- 問題長度改成「去掉頭尾空白後」才算 200 字；`RATE_LIMIT_REQUESTS`、`RATE_LIMIT_WINDOW_SECONDS` 必須 ≥ 1。
- `GET /api/chunks/{id}`：沒有 `:` 的 id、或指名了不存在的項（`-p9`）回 404（原本分別是 500 與退回第一塊）。
- 已知但未處理：部署在反向代理後要設 `TRUST_PROXY`，且多層代理時取最後一個 `X-Forwarded-For` 會落到最外層代理的 IP（Step 12 要設定並實測）；`lru_cache` 建構沒有鎖（冷啟動時兩個同時請求可能各建一份，無害）。
