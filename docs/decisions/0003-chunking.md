# ADR 0003：Chunking 策略

狀態：已採用（Step 3）；門檻與切法待 Step 4 的評估數字驗證

## 背景

檢索與引用的單位是 chunk。chunk 太大，向量被不相關內容稀釋，餵給 LLM 的 prompt 也變長；太小，單獨看不出意思（「前項規定者，處…」），也容易把一條條文的條件與罰則拆散。UI 以「條」為單位呈現，所以 chunk 必須能對回所屬條文。

資料長度（2026-10-05 版，462 條）：中位數 112–194 字，95% 的條文在 800 字以內；超過 800 字的有 22 條，最長 2,474 字（道安規則第 39 條）。

## 選項

1. **固定長度滑動視窗**（如 500 字、重疊 50）：實作最簡單，但會在句子中間或條文邊界切開，引用時對不回「第幾條」。
2. **一條一個 chunk，不切**：最貼近法律的結構，但最長 2,474 字的條文會稀釋向量，也讓 prompt 很長。
3. **一條一個 chunk，過長才依「項」切**（spec 的方向）：保留條文邊界，只在必要時切。但道安規則 39、39-1 是單一項就超過 2,000 字，只切項切不開。

## 決定

採用選項 3，並加上兩條補充規則：

1. 條文 ≤ 800 字：整條一個 chunk，`chunk_id = {pcode}:{article_no}`。
2. 超過 800 字：把「項」依序累加到 800 字，不在項中間切。chunk_id 為 `{pcode}:{article_no}-p{n}`。
3. **單一項超過 800 字：退到「款」（一、二、三…）的邊界切**（對 spec 的延伸）。實測沒有任何單一款超過 800 字，所以不需要切在句子中間。
4. **`-p{n}` 的 n 是 chunk 序號**，`paragraph_no` 記錄該 chunk 從第幾項開始。款層級切分時，不同 chunk 可能都從同一項開始，用項號當 id 會撞號（對 spec 的延伸）。
5. **短尾巴併回前一塊**：最後一塊不到 100 字就併入前一塊，所以 chunk 最長 900 字。這樣不會出現只有一句「前項…」的孤兒 chunk。併完只剩一塊時，chunk_id 回到 article_id。
6. `embed_text` = `{法規全名} {章節} 第 {條號} 條` 加換行與原文。每個切出來的 chunk 都帶同樣的標題，切碎後仍看得出屬於哪一條。
7. 刪除條文（`（刪除）`）在 Step 2 已排除，不會產生空 chunk。

結果：462 條 → 約 488 個 chunk，平均約 243 字，最長 864 字；21 條被切成多塊。

## 為什麼是 800 字

這是 spec 給的起點，不是實驗出來的值。它大致讓 95% 的條文維持「整條一塊」，被切的都是真正的長條文。Step 4 建立評估集後，會用 Recall@5 與 MRR 比較不同上限（例如 500／800／1200），再決定要不要改。

## 放棄了什麼／已知限制

- **款層級切分會丟失引導句**：像道安規則第 39-1 條「汽車定期檢驗之項目及基準，依下列規定：」只在第一塊，後面幾塊只有「十一、…」。單看後面的塊，語意不完整，向量檢索可能較難命中。`embed_text` 的標題有帶條號但沒帶引導句。若評估顯示這類條文表現差，再考慮把引導句也加進後續塊的 `embed_text`（不改 `text`）。
- **條文互相引用**（「依第三十五條規定」）不處理：chunk 之間沒有連結。
- **「條」層級的檢索結果合併**留給 UI／Step 8：同一條被切成多塊且都被檢索到時，只顯示一張卡片。
- **向量不保證逐位元相同**：embedding 來自外部 API。「重跑結果一致」以 chunk 的 id 與內容完全相同為準（有測試），並且每次重建索引都是整個重來，不做增量，所以不會累積舊資料。

## 後果

- `-p{n}` 的 chunk 都能由 id 去掉後綴得到 `article_id`，`/api/chunks/{id}` 可回該條整條全文。
- 改動 chunk 大小或規則後必須重建索引並重跑評估（Step 4 之後的規則）。
